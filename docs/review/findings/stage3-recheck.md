## 1번 과제 결론 (400 / 401)

### 400 PGRST102 = 기사 리드문 사본 저장 실패 (1793)
- **로그 위치** : `[캐시 Supabase 저장 실패]` 문구는 1793 한 곳에만 있다. 응답 캐시 쪽 로그는 2767(성공)과 2769(실패)다. (`grep -n "캐시 Supabase 저장 실패" server.js`)
- **원인 줄** : 요청 본문을 만드는 곳 1785, 재료 1774–1779. 글자는 세 번 잘린다 — 1991 에서 6000자, 1828 에서 4000자, 1778 에서 800자.
- **PostgREST 소스로 확인** ([Payload.hs](https://github.com/PostgREST/postgrest/blob/main/src/library/PostgREST/ApiRequest/Payload.hs)) : PGRST102 "Empty or invalid json" 은 받은 본문을 aeson `JSON.decode` 가 못 읽었을 때만 난다. 이 경로에 크기 검사는 없다.
- **우리 쪽 본문은 정상** : JSON.stringify 결과를 그대로 보내고, 그 뒤에 자르거나 고치는 곳이 없다. 빈 본문이 나가는 길도 없다(0건이어도 `[{"key":…,"value":[]}]`). 가짜 Supabase 기록(공유 서버 :3100 의 실제 저장 요청) : content-length 656,042 = 실제 656,042 바이트, 나눠 보내기(chunked) 아님, JSON 정상.
- **aeson 이 거부할 수 있는 것은 사실상 하나** : 짝 없는 서로게이트 이스케이프(이모지 반쪽). Node 에서 `'가😀'.slice(0,2)` 를 직렬화하면 `"가\ud83d"` 가 나온다(실행 확인). aeson 소스([Unescape.hs](https://github.com/haskell/aeson/blob/master/src/Data/Aeson/Internal/Unescape.hs) 104–110, 186–195)는 이것을 `throwDecodeError` 로 거부한다.
- **`\u0000` 은 원인 아님** : aeson 은 통과시키고 Postgres 가 22P05 로 거부하므로 메시지가 다르다. 로컬 표본에서도 0건.
- **로컬 측정** (리뷰어 `measure-article.js` 로 `.cache/article-text.json` 을 1774–1789 와 같은 방식으로 직렬화) :
  - 369건, 본문 656,042B. 1건에 1,778B 꼴 → 1500건이면 약 2.67MB.
  - 4바이트 글자(이모지 등) 666,281자 중 8개(기사 5건), 짝 없는 서로게이트 0.
  - 800자로 잘린 줄 300/369. 여기서 계산하면 저장 1번에 반쪽 이모지가 생길 확률 약 1.5%.
  - 한 번 생기면 그 기사가 '최근 1500건 · 6시간' 안에 남아 있는 동안 30분마다 다시 실패(1794–1795 가 간격을 되돌림).
- **결론 : 증명 못 함.**
  - 후보 A : 잘린 이모지 → 짝 없는 서로게이트. 코드에서 PGRST102 와 맞는 유일한 길. 다만 로컬 빈도로는 자주 나는 오류를 다 설명하기 어렵다.
  - 후보 B : 본문이 Supabase 앞단에서 비거나 잘린 채 도착. 코드 쪽 근거는 없고, 2.7MB 크기와 관련될 수 있다.
  - 판정 방법 : 아래 "사용자에게 확인할 것" 의 로그 시각 패턴. 또는 단계 10 에서 1793 catch 에 `Buffer.byteLength(본문)` 과 짝 없는 `\ud8xx` 개수를 찍는 진단 로그 1줄 → 다음 실패 한 번으로 A/B 가 갈린다.
- **방어할 때 주의** : `.toWellFormed()` 는 직렬화 **전** 글자(1778 또는 1828)에 걸어야 한다. 직렬화한 뒤 문자열에 걸면 이미 `\ud83d` 라는 영문 6글자로 바뀐 뒤라 효과가 없다(실행 확인).

### 401 PGRST303 "JWT issued at future" — 코드 문제 아님, 보고만
- PostgREST 소스([Jwt.hs](https://github.com/PostgREST/postgrest/blob/main/src/library/PostgREST/Auth/Jwt.hs), Auth.hs) : 서명 확인을 통과한 JWT 의 발급 시각(iat)이 PostgREST 자기 시계 + 30초보다 뒤일 때 이 메시지가 난다.
- 로컬 키 `sb_secret_…` 는 JWT 가 아니라 iat 자체가 없다 → 거부된 JWT 는 우리 앱이 만든 것이 아니다. 서명까지 맞았으니 프로젝트 서명 키를 가진 Supabase 쪽(앞단이 키를 내부 JWT 로 바꿔 넘김)이 만든 것이다.
  - [자체 호스팅 문서](https://supabase.com/docs/guides/self-hosting/self-hosted-envoy)에는 미리 서명해 둔 JWT 로 바꾼다고 나온다. 클라우드에서 요청마다 새로 만드는지는 문서에 없다 → **추정**.
- Render 가 옛 방식 키(`eyJ…`)를 쓴다면 iat 는 발급한 날(과거)이라, '미래' 판정은 PostgREST 시계가 틀렸을 때만 나온다.
- 어느 경우든 Render 시계·앱 코드와 상관없다. 1806 과 2779 는 같은 머리말(139–145)로 5ms 차이(가짜 로그 :54.039 / :54.044)로 나가는데 운영에서는 하나만 실패 → Supabase 쪽 일시 문제.
- 키 재발급은 효과가 의심스럽다(추정).
- 곁가지(범위 밖) : Supabase 문서는 새 키를 `apikey` 머리말에만 넣으라고 한다([API keys](https://supabase.com/docs/guides/api/api-keys)). 139–145 는 `Authorization: Bearer` 에도 넣는다. 다만 이것이 원인이면 iat 메시지가 아니라 JWT 해석 오류가 났어야 하므로 이번 401 과는 무관.
- 이 일시적 401 이 키워드 읽기(611)에 걸리면 F3 이 터진다.

## fetchHtml SSRF 질문에 대한 답

- **같은 검사를 거치지 않는다.** fetchPageHead(3879)는 ① imageUrlAllowed(3814) ② safeLookup 내부 IP 차단 ③ `redirect: 'manual'`(3887)로 재전송마다 검사한다. fetchHtml(1995–2014)은 셋 다 없다. 기본 DNS 를 쓰고 `redirect: 'follow'` 로 아무 검사 없이 따라간다.
- **주소가 오는 곳은 두 군데.**
  - 섹션 검증(2078 · 2106 · 2154) : 네이버가 준 originallink/link(2316). 사용자는 못 넣는다. 다만 언론사 서버가 302 로 내부 주소를 가리키면 따라간다. 결과는 화면에 안 나오고 캐시와 Supabase 사본(800자)에만 남는다.
  - **/api/deep-brief(5004) · /api/insight(5127)** : 주소창의 `url` · `naver` 를 그대로 쓴다. 검사는 `^https?://` 하나뿐. 허용된 사용자가 자기 Gemini 키를 등록하면 `?url=http://127.0.0.1:…` 나 내부망 주소를 서버가 대신 읽고, 그 내용을 Gemini 가 요약해 돌려준다. 성공·실패 문구가 달라 포트 탐색도 된다. 읽은 글은 캐시 → 로컬 파일 → Supabase 사본으로도 퍼진다.
- **재현** : fetchHtml 사본으로 `http://localhost:p/news/1` → 302 → `http://127.0.0.1:q/admin` 을 읽어 내부 글을 받았다(`ssrf-demo.js`). 라우트 끝까지는 AI 키를 흉내 내야 해서 하지 않았다.
- **실제 위험 : 중.** 허용된 사용자와 본인 키가 필요하다. 피해 크기는 Render 내부망에 다른 서비스가 있느냐에 달려 있다. 고치는 방향은 c-ares agent 를 재사용하는 것이라 F2 와 같은 결정 → **보호 목록 인접 — 사용자 결정 필요**.

## 사용자에게 확인할 것
1. **Render → 서비스 → Environment → `SUPABASE_SERVICE_KEY`** : 값이 `sb_secret_` 로 시작하는지 `eyJ` 로 시작하는지 **앞글자만**.
2. **Render → Logs 에서 아래 문구 검색**
   - `캐시 Supabase 저장 실패` : 나온 시각들. 30분 간격으로 몇 시간 이어지다 멈추면 후보 A, 배포 몇 시간 뒤부터 매번이면 후보 B 쪽. 바로 앞의 `[프리워밍] 완료 … 본문 캐시 X → Y건` 의 Y 도 같이.

   - `Supabase에서 응답` / `응답 캐시 Supabase 복원 실패` : 배포할 때마다 나는지.
   - `[프리워밍] 키워드 조회 실패` : 있으면 F3 이 실제로 일어난 것.
