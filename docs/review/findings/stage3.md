## 1번 과제 (Supabase 사본 400/401)
- 문서 해석이 틀림 : 400 로그 `[캐시 Supabase 저장 실패] HTTP 400` 은 server.js:1793 = **기사 리드문 사본 저장**(saveArticleCacheToSupabase). 응답 캐시 저장 로그는 2767(성공)/2769(실패). 401 `[응답 캐시 Supabase 복원 실패]` 는 2801. → PERFORMANCE.md:113 "응답 캐시가 저장도 복원도 안 된다"는 로그 두 줄로는 뒷받침 안 됨. 판정법 : Render 로그에서 `[캐시] 응답 N칸(…KB)을 Supabase에 저장했습니다`(2767) 검색.
- 400 원인 줄 : 본문 생성 1785(재료 1775–1779). 코드 구조는 정상(복원은 성공했으므로). 후보 A 크기 — 건수 상한 1500(1715)만 있고 바이트 상한 없음(664건=1.17MB, 1500건≈2.6MB). 후보 B 깨진 글자 — 1778 slice(0,800), 1828 slice(0,4000), 1991 slice(0,6000) 이 이모지를 반으로 자르면 짝 없는 서로게이트 → JSON 거부 가능(로컬 표본 0건, 운영 미확인). 판정 : 1793 catch 에 Buffer.byteLength 와 짝 없는 글자 수 로그 추가(+ `.toWellFormed()` 로 방어). 로컬 검증 N. 부수 : 실패하면 1794–1795 가 간격을 되돌려 30분마다 1~2.6MB 재업로드 시도.
- 401 : 코드 문제 아님(보고만). 1806 과 2779 는 같은 supabaseHeaders() 를 쓰고 같은 순간 하나는 성공·하나는 401 → 일시적/시계 문제. 키 재발급은 효과 의심. 완화(선택) : 2801 실패 시 1~2초 뒤 1회 재시도.
